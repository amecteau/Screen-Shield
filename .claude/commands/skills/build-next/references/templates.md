## Phase format rules

When generating phases, follow these rules:

1. **Phase 0 is always scaffold** — config files, CI definitions, shared types with no business logic. Phase 0 has NO logic tests; it just needs to compile.

2. **One concern per phase** — don't mix "add feature X" and "add feature Y" in the same phase even if they're small. Smaller phases = easier rollback.

3. **Explicit file paths** — every phase lists every file it creates. No surprises.

4. **Tests are part of the phase** — the test file for `foo.ts` is written in the same phase as `foo.ts`, not a separate phase.

5. **When-done is a command** — "when done" must be a runnable shell command the agent can execute to verify, e.g., `npx vitest run src/module/ && npx tsc --noEmit`.

6. **Security-critical phases get a note** — if a phase creates security boundaries (auth, IPC, input validation), add: `**Security note:** These tests guard [boundary]. If any fail, nothing else matters.`

7. **Phase N-1 is integration wiring** — one phase near the end that connects all modules at the entry point with no business logic of its own.

8. **Phase N is E2E** — the final phase is end-to-end tests using whatever E2E framework was chosen.
